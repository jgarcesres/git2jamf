# git2jamf v2 design

- **Date:** 2026-10-04
- **Status:** draft, awaiting review
- **Tracking:** jgarcesres/git2jamf#26 (milestone `v2`)

## Goal

Rewrite git2jamf as v2: sync scripts **and computer extension attribute scripts** from a Git repository to Jamf Pro. Fix every defect found in the v1 review, make deletes safe by design, and make the action testable without access to a Jamf Pro instance.

v1 code is not changed. The only v1 release is a docs-and-warning patch (v1.4.1) to prepare `@main` users for the cutover (see [Release and migration](#release-and-migration)).

## Success criteria

1. All issues in milestone `v2` are closed by the rewrite: #8, #10, #14 to #25.
2. CI is green: lint, format, unit, contract and end-to-end tests, plus the action itself run via `uses: ./` against the fake Jamf server.
3. Coverage is at least 95% (branch coverage), and `plan.py` is at 100%.
4. At least one user with a real Jamf Pro instance reports a correct `dry_run` plan from a `v2.0.0-beta.N` pre-release before `v2.0.0` ships.

## Non-goals

- Mobile device or user extension attributes. Jamf only supports the script input type on computer extension attributes.
- Extension attributes with input types other than script (text field, pop-up menu, directory service mapping).
- Creating categories. Categories are referenced by name and must already exist.
- Packages, policies, profiles or any other Jamf object.
- Backwards compatibility with v1 inputs. v2 is a clean break, with a migration guide and loud errors for v1-only inputs.

## Decisions

| Topic | Decision | Reason |
|---|---|---|
| Runtime | Python 3.13 in the action (`requires-python >= 3.11` for local `uvx` use), composite action using `actions/setup-python` and `astral-sh/setup-uv`, dependencies locked in `uv.lock` | Familiar to Mac admins; no per-run image build; the same package runs locally via `uvx` for beta testers |
| Runtime dependencies | `requests`, `PyYAML` | Small surface; nothing else needed at runtime |
| Compatibility | Clean break, migration table in README, v1 inputs fail with a clear message | Major version; tag pinning protects users who pin |
| Per-object settings | Optional YAML sidecar next to each script (`cleanup.sh` + `cleanup.yml`) | Script is uploaded byte-for-byte; adoption is incremental |
| Ownership | Marker block at the top of `notes` (scripts) or `description` (extension attributes) | Jamf has no tags or custom fields on these objects; the marker is visible to admins and survives round trips |
| Delete scope | Only objects whose marker matches this run's `owner` and `prefix` exactly | Hand-made objects, other repos and other branches are never touched |
| Jamf API | Jamf Pro API (`/api/v1/...`) only; no Classic API | Classic API needs XML and basic auth; the Jamf Pro API covers everything needed |

## Architecture

```
action.yml                    composite action
pyproject.toml, uv.lock
src/git2jamf/
  config.py                   inputs -> Settings (validated)
  local.py                    filesystem scan -> LocalObject list
  metadata.py                 sidecar schema and validation
  plan.py                     pure planning logic -> Plan
  jamf.py                     JamfClient (HTTP)
  apply.py                    executes a Plan via JamfClient
  report.py                   log output, step summary, action outputs
  cli.py                      entry point `git2jamf`
tests/
  unit/                       config, metadata, local, plan, report
  contract/                   client requests and fake responses vs OpenAPI
  e2e/                        CLI against the fake server
  fake_jamf/                  in-memory Jamf Pro API server
  openapi/                    vendored OpenAPI definitions
scripts/fetch_openapi.py      refreshes tests/openapi from developer.jamf.com
```

### Units

**`config.py`.** Builds a frozen `Settings` dataclass from `INPUT_*` and `GITHUB_*` environment variables (action mode) or CLI flags (local mode). It validates everything before any network call:

- `jamf_url` is an `https://` URL; a trailing slash is stripped. `http://` is allowed only for `localhost` and `127.0.0.1`, which the tests need.
- Exactly one credential pair is set, either client ID and secret or username and password. Both pairs, or neither, is an error.
- At least one of `script_dir` and `ea_dir` is set. Relative paths are resolved against `GITHUB_WORKSPACE`, or the current directory in local mode; absolute paths are used as given. Each must exist and be a directory, and `ea_dir` may not equal `script_dir`.
- `prefix`: the values `true` and `false` (any case) are rejected with a pointer to the migration guide.
- Booleans accept `true` and `false` (any case) only.
- `owner` is non-empty. In action mode it defaults to `GITHUB_REPOSITORY`. In local mode there is no default, and `--owner` is required, so a laptop run can't accidentally claim another scope.

**`metadata.py`.** Parses and validates a sidecar. Unknown keys are an error, which catches typos. Schemas:

Script sidecar:

| Key | Type | Jamf field |
|---|---|---|
| `category` | string (category name) or `null` for none | `categoryId` |
| `priority` | `BEFORE` \| `AFTER` \| `AT_REBOOT` | `priority` |
| `info` | string | `info` |
| `notes` | string | text below the marker in `notes` |
| `parameters` | map of integer 4 to 11 -> string label | `parameter4` to `parameter11` |
| `os_requirements` | string | `osRequirements` |

Extension attribute sidecar:

| Key | Type | Jamf field |
|---|---|---|
| `description` | string | text below the marker in `description` |
| `data_type` | `STRING` \| `INTEGER` \| `DATE` | `dataType` |
| `inventory_display` | `GENERAL` \| `HARDWARE` \| `OPERATING_SYSTEM` \| `USER_AND_LOCATION` \| `PURCHASING` \| `EXTENSION_ATTRIBUTES` | `inventoryDisplayType` |
| `enabled` | boolean | `enabled` |

`inputType` is always `SCRIPT`.

**`local.py`.** Scans `script_dir` recursively for files with extensions in `script_extensions`, excluding anything under `ea_dir`. It scans `ea_dir` recursively with the same extensions. For each file it produces `LocalObject(kind, name, path, contents, metadata)`:

- `kind` is `script` or `extension_attribute`.
- `name` is the file stem, prefixed as `{prefix}_{stem}` when `prefix` is set.
- `metadata` comes from a sidecar with the same stem and a `.yml` extension, if one exists. A `.yml` file with no matching script is reported as a warning.
- Files are read as UTF-8; a decode error fails with the file path.

**`plan.py`.** A pure function, `build_plan(local, remote, settings) -> Plan`. No I/O. `Plan` is a list of `Action(kind, verb, name, local, remote, changes)`, where `verb` is one of `create`, `update`, `adopt`, `unchanged`, `delete` or `orphaned`. `orphaned` (owned by this run's scope but no longer present locally, with `delete: false`) is reported and never written. Rules are in [Sync semantics](#sync-semantics).

**`jamf.py`.** `JamfClient`:

- One `requests.Session`. Every request has a timeout (10 s connect, 60 s read).
- Retries with backoff, 3 attempts, honouring `Retry-After`:
  - `GET`: on 429, 502, 503, 504 and connection errors.
  - `POST`, `PUT` and `DELETE`: only on 429, which Jamf rejects without processing. A write that hits a 5xx or a connection error is not retried, because it may have been applied (a retried create could duplicate a script). It fails, and the next run's plan reconciles.
  - Other status codes raise immediately.
- **Auth.**
  - With a client ID and secret: `POST /api/v1/oauth/token` (form-encoded `client_credentials`). If that returns 404, fall back once to `POST /api/oauth/token` for older Jamf Pro versions.
  - With a username and password: `POST /api/v1/auth/token` (basic auth).
  - The token is refreshed when it is within 60 s of expiry, and once more on any 401.
  - `close()` calls `POST /api/v1/auth/invalidate-token` and logs, rather than raises, any failure. `cli.py` calls it in a `finally` block.
- **Listing.** Pagination is a loop with `page-size=200`, following `totalCount`.
- **Scripts.** `GET /api/v1/scripts`, `POST /api/v1/scripts`, `PUT /api/v1/scripts/{id}`, `DELETE /api/v1/scripts/{id}`.
- **Extension attributes.**
  - `GET /api/v1/computer-extension-attributes`. The full object, including `scriptContents`, is fetched with `GET /api/v1/computer-extension-attributes/{id}` for each candidate whose name matches a local object or whose description carries this run's marker.
  - Writes: `POST`, `PUT /{id}` and `DELETE /{id}`.
  - Dependency check: `GET /api/v1/computer-extension-attributes/{id}/data-dependency`.
  - A 404 on the list endpoint fails with "this Jamf Pro version does not support extension attributes through the Jamf Pro API".
- **Categories.** `GET /api/v1/categories`, fetched only if a sidecar references a category.
- **Errors.** A failed request raises `JamfError(method, path, status, body excerpt)`. The body excerpt is truncated to 500 characters, and credentials and tokens are never logged.

**`apply.py`.** Executes a `Plan`:

- `create`, `update` and `adopt` run first, in plan order. A failure on one object is recorded and the rest continue.
- `delete` runs only if no earlier action failed. If any did, deletes are reported as skipped.
- For extension attribute deletes, the data-dependency check runs first. A non-empty result marks that delete as failed and lists the dependents.
- In `dry_run` mode nothing is written. Reads, including the dependency check, still run, so the dry-run plan matches what a real run would do.

**`report.py`.**
- Writes one log line per action and the step summary: a Markdown table of kind, name, verb and detail, with failures first.
- Sets outputs through `$GITHUB_OUTPUT`: `created`, `updated`, `deleted` and `unchanged` as JSON arrays of names (`adopt` counts as `updated`), and `changed` as `true` or `false`. In dry-run mode the outputs describe the plan.
- Uses GitHub annotations (`::error::`, `::warning::`) for failures and warnings.

**`cli.py`.** Entry point `git2jamf`. Order: config, local scan, client login, remote fetch, plan, apply, report. Exit codes: 0 on success, 1 on any failed action, 2 on configuration or validation error. Failures in remote fetch or planning, including collisions, exit 1 before any write.

## Sync semantics

**Naming and collisions.** Names are compared case-insensitively. The following are errors detected while planning, before any write:
- two local objects of the same kind with the same name
- a local object whose name matches more than one remote object of the same kind

Scripts and extension attributes are separate namespaces.

**Marker block.** The first lines of `notes` (scripts) or `description` (extension attributes):

```
git2jamf: owner=<owner> prefix=<prefix or empty>
git2jamf: created <YYYY-MM-DD>
git2jamf: updated <YYYY-MM-DD> (commit <short sha>)
<user text>
```

- Every consecutive leading line that starts with `git2jamf:` belongs to the block. Everything after it is user text.
- On create, the `updated` line is omitted.
- On update, `created` is kept and `updated` is replaced.
- On adopt, an existing `created` line is kept; otherwise `created` gets today's date. Existing user text is kept. This covers #8, including scripts v1 created with the note `created via github action`, which stays as user text.
- If the sidecar has `notes` (or `description`), that replaces the user text. Otherwise the user text in Jamf is kept.
- The commit SHA comes from `GITHUB_SHA`. In local mode the parenthetical is omitted.

**Change detection.** An object is `unchanged` when:
- its contents are equal after normalizing `\r\n` to `\n`, and
- every field set in its sidecar equals the remote value, with user text compared after stripping the marker block.

The marker's dates are never compared, so an unchanged object is never rewritten.

**Verbs:**

| Local | Remote match | Remote marker | Result |
|---|---|---|---|
| present | none | | `create` (sidecar values, else defaults) |
| present | one | matches owner and prefix | `update` if changed, else `unchanged` |
| present | one | absent | `adopt` (writes marker; also applies content and sidecar changes) |
| present | one | different owner or prefix | error: owned by another repo or branch |
| absent | | matches owner and prefix | `delete` if `delete: true`, else reported as `orphaned` (no write) |
| absent | | absent or other owner | ignored, not reported |

Create defaults:
- Scripts: no category (`categoryId` `-1`), priority `AFTER`, empty parameters.
- Extension attributes: `STRING`, `EXTENSION_ATTRIBUTES`, enabled.

**Safety rails:**
- If `delete: true` and the scan found zero local objects of a kind whose directory is configured, the run fails before any write.
- An extension attribute delete is refused when the data-dependency check returns dependents.

## Error handling

- Configuration errors: exit 2 with one `::error::` per problem. All problems are reported together, not just the first.
- Remote fetch or planning errors: exit 1 before any write.
- Write errors: recorded per object, the remaining creates and updates continue, deletes are skipped, exit 1.
- No broad exception catching except at the top level in `cli.py`. That handler prints the error and exits 1, and token invalidation runs in `finally`.
- Logs never contain credentials, tokens or full script contents.

## Testing

No Jamf Pro instance is available, so confidence comes from four layers.

1. **Unit tests** (`pytest`, table-driven).
   - `plan.py`: every row of the verb table, collisions, prefix and owner scoping, the marker-block parsing and rewriting, change detection including CRLF, and the safety rails.
   - Plus `config`, `metadata`, `local` (with `tmp_path`) and `report`.
2. **Contract tests.**
   - `scripts/fetch_openapi.py` downloads the OpenAPI definition embedded in each endpoint's page on developer.jamf.com (`https://developer.jamf.com/jamf-pro/reference/<slug>.md`) into `tests/openapi/<slug>.json`.
   - Tests validate every request body `JamfClient` sends, and every response the fake server returns, against those schemas using `jsonschema` (a dev dependency).
3. **Fake Jamf server** (`tests/fake_jamf/`).
   - Standard-library `ThreadingHTTPServer` with in-memory stores.
   - Implements exactly the endpoints in `jamf.py`, with Jamf's pagination and token expiry (401), and records every request.
   - Fault injection: 429 with `Retry-After`, 500, slow responses, a 404 on the v1 OAuth path, and a 404 on the extension attribute endpoints.
   - It can also run standalone (`python -m tests.fake_jamf`) for the CI action job.
4. **End-to-end tests.**
   - Run `git2jamf` as a subprocess against the fake server, using fixture repositories.
   - Assert the server's final state, the exit code, the outputs file and the step summary.
   - Scenarios: first run creates; second run is a no-op; content change updates; sidecar change updates; adoption of v1 objects; delete scoping across owners and prefixes; dry run writes nothing; auth failure exits non-zero; partial failure skips deletes; extension attribute dependency refusal.

**CI (`.github/workflows/ci.yml`).**
- Runs on pull requests and on pushes to `main` and `v2`.
- Jobs:
  - `lint`: `ruff check` and `ruff format --check`
  - `test`: `pytest` with branch coverage, failing under 95%
  - `action`: starts the fake server, runs `uses: ./` twice (dry run, then real), and checks the outputs

**Drift check (`.github/workflows/openapi-drift.yml`).** Runs weekly. It runs `scripts/fetch_openapi.py` and fails if `tests/openapi/` changed, so a Jamf API change shows up as a red build.

## Release and migration

Current state: tags `v1` to `v1.4` exist, and none move. `v1` points at the 2020 code. The README tells users to pin `@main`, which is v1.4. No public workflows reference the action (code search, 2026-10-04), so users can't be contacted directly.

1. **Development.** Work happens on branch `v2`, in PRs against `v2`.
2. **v1.4.1 (on `main`, the only v1 change).**
   - README: a banner telling users to pin `@v1.4` or move to `@v2`, and the brownout schedule.
   - `action.py`: a startup check that emits a `::warning::` on every run with the same message.
   - During listed brownout windows (hard-coded UTC start and end times), it emits `::error::` and exits 1 **before any Jamf request**.
   - Released as tag `v1.4.1`. Existing tags are untouched, so pinned users see nothing.
3. **Betas.**
   - Publish `v2.0.0-beta.N` as GitHub pre-releases from `v2`.
   - Open a pinned "Try v2" issue, with an issue template for dry-run reports covering the Jamf Pro version, the plan output and any errors.
4. **Brownouts.** At least three windows, at least a week apart and escalating: 4 h, 8 h, then 24 h. Each is announced in the pinned issue and README before it starts.
5. **v2.0.0.**
   - Merge `v2` into `main`. Tag `v2.0.0` and a moving major tag `v2`.
   - The README pins `@v2` and includes the migration table: v1 input to v2 input, and behaviour changes.
   - From then on, `@main` users who ignored the brownouts get v2's configuration errors (`prefix: true`, removed inputs, missing `script_dir`), never silent wrong behaviour.
6. **Cleanup.** Close or supersede PRs #9 and #11 (maintainer's decision), and remove the Dockerfile, `requirements.txt`, `ea_script_template.xml` and the old CI workflow on `v2`.
